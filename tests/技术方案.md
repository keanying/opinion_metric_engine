# 06 · APP 端接 IdP（不置换）**实际改动点** —— 旧表兼容版

> **做什么**：把 APP 端的登录与身份识别交给票付通 3.0 的 IdP——前端拿 IdP token 来请求我们，我们从 token 认人。**分工**：用户的账号属性（姓名 / 手机号 / 密码）归 IdP，`scenic_id` / `role` 归我们的管理端，用户表、景区、permission 判定和鉴权之后的全部业务逻辑一个字不改。
>
> **怎么做**：
>
> 1. `usr_users` 加一组 `idp_*` 列（迁移 `0093`），以 `(tenantId, userId)` 唯一认人；表结构之外——外键、Casbin 策略、审计口径——一律不动。
> 2. 新增 `POST /api/app/auth/sync`：登录时认人 / 自动建号、记一条 `LoginDevice`、刷新镜像。
> 3. `deps.py:90` 换成每请求三步：验 IdP token → 按 `(tenantId, userId)` 查 `usr_users` → 组装出和今天一模一样的 `CurrentUser`。token 里的 claims 直接带上（`permissions` 每次都是最新值，**不读镜像列做判定**）。
> 4. `routes_app.py` 里 11 处误用管理端 `get_current_user` 的改成 `get_current_app_user`；管理端那条链路不动。
> 5. `GET /me` 的姓名 / 手机号改取 IdP 镜像列（带本地值回落），并作为镜像的即时刷新点；`POST /me` 前端不再调用。镜像其余时候按时间窗口惰性刷新。
> 6. IdP 权限 → APP 分类的映射入库（迁移 `0094` + 管理端维护页），`list_fixed_for_app` 按它过滤固定问题；**没配到映射 = 返回空**，不是全放行。
> 7. 旧的 APP 端注册 / 登录 / 改密 / 短信验证码 / 刷新 token 接口**不动也不用**（前端不调用），是否下线待定。

## 名词解释（先对齐这三个词）

| 名词 | 在本文中指什么 |
|---|---|
| **IdP** | Identity Provider，身份提供方。**本文特指「票付通 3.0」的登录 / 认证系统**——用户账号、密码、登录态都由它负责，我们不再自己处理凭据。文中所有 `idp_*` 均指它 |
| **IdP token** | 用户在票付通 3.0 登录成功后，由 IdP 签发、APP 持有的登录凭证。APP 每次请求我们后端都带着它 |
| **不置换** | 我们**不签发任何自有 token**、**不保管 IdP 凭证**；IdP token 全程就是请求的身份凭证，每个请求都验一次 |

**IdP token 已确认能解析出这些信息**（本次设计的全部输入都来自这里）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `userId` | integer\<int64\> | 平台用户 ID |
| `userName` | string | 用户名称 |
| `phone` | string | 手机号 |
| `tenantId` | integer\<int64\> | 租户 ID |
| `permissions` | array[string] | 权限编码列表 |
| `roles` | array[string] | 角色编码列表 |

> **`tenantId` + `userId` 合起来才是 IdP 侧的用户唯一标识**——单看 `userId` 在不同租户下可能重复，这是本次数据建模的第一约束。

## 0. 一句话说清这版方案

**本次迭代的核心只有一句：APP 端「登录 + 权限」的来源，从我们自己的帐密换成票付通 3.0 的 IdP；除此之外一切不变。**

用户还是 `numeri_core_usr_users` 里那一行，账号还是管理后台建，景区/角色还是管理后台配，permission 判定还是那份 Casbin 策略——变的只有"APP 怎么证明我是谁"和"我们从哪认出他"。

```
登录   前端 → IdP → 拿 IdP token → 调我们一次 /api/app/auth/sync（认人 + 记设备）
请求   前端 → 我们 [Bearer <IdP token>]
             ├─ 1 idp_verify(token)              → tenantId + userId +（userName/phone/roles/permissions 都在 token 里）
             ├─ 2 按 (tenantId,userId) 查 usr_users → id / scenic_id / role / is_active
             └─ 3 组装 CurrentUser → 后面所有业务逻辑**完全按原样跑**
```

**因为 token 自带用户信息，不需要额外调用 IdP 的用户接口**——每请求对外部的依赖只剩"验 token"这一次。第 3 步往后与今天一字不差：`CurrentUser(user_id, scenic_id, role)` 结构没变，`user_id` 还是原来那个 id。

## 1. 为什么"不动表"是这个迭代的正确解法

新 id 空间一旦脱离 `usr_users`，会引发一批静默失效（查不到行、不报错、只是结果变少）。**这些麻烦在旧表兼容版里根本不存在**：

| 位置 | 新表方案会遇到 | 旧表兼容 |
|---|---|---|
| `user_center_service/models.py:41` `LoginDevice.user_id` 外键 | 写入违反外键，必须 DROP | **不用动** |
| `user_center_service/models.py:141` `AppConfig.user_id` 外键 | 同上 | **不用动** |
| `control_plane_service/models.py:32/71/103/127/146`（任务/会话/消息/反馈/关注） | id 空间变了，**历史数据全部对不上** | **不用动，历史会话/任务原样继承** |
| `cronjobs/prewarm_v2.py:636-642` 预热景区范围 | 只有 IdP 用户的景区**永远不预热** | **不用动** |
| `gateway_service/ota_accounts.py:62-70` `AppConfig join User` | join 断裂，OTA 派单静默丢数据 | **不用动** |
| `user_center_service/scenics.py:24-40` 景区用户数 | 口径变小 | **不用动** |
| 管理端用户管理页（建号/配景区/角色/停用） | 要新建一整套平行接口 + 新菜单 | **不用动，沿用现有 `/users/*`** |

一句话：**新 id 的成本全在业务之外的地方。** 本次只改登录入口，没必要为它引入第二套用户体系。

> 什么情况下会重新考虑新表：APP 用户量级起来、且与管理端员工账号彻底无关（例如面向 C 端游客）。现在不是这种情况。

## 2. 数据模型：给 `usr_users` 加一组 `idp_` 列

### 2.1 新增列（`user_center_service/models.py`，加在 `:29 credentials_changed_at` 之后）

**命名约束：新增字段一律 `idp_` 前缀**，一眼能看出"这些列由 IdP 侧信息写入，本地业务不直接改"。

| 字段 | 类型 | 必选 | 说明 |
|---|---|---|---|
| `idp_tenant_id` | BigInteger nullable | ✅ | IdP 的 `tenantId` |
| `idp_user_id` | BigInteger nullable | ✅ | IdP 的 `userId` |
| `idp_synced_at` | DateTime nullable | ✅ | 最近一次同步时间（**不用 `last_login_at`，见 §6.1**） |
| `idp_user_name` | String(64) nullable | 可选 | 镜像 `userName`，排障/核实用 |
| `idp_phone` | String(32) nullable | 可选 | 镜像 `phone`，**仅展示与人工核实，不参与本地登录** |
| `idp_roles` | JSON nullable | 可选 | 镜像 `roles`，**本次不参与鉴权**，见 §2.4 |
| `idp_permissions` | JSON nullable | 可选 | 镜像 `permissions`，同上 |

**唯一标识 = `idp_tenant_id` + `idp_user_id` 的复合唯一索引**（部分索引，见 §2.2）。单独给任何一个加唯一约束都是错的——跨租户 `userId` 会重复。

> **不新增不成阅兵式的 `status` 列**，继续复用现有语义：
>
> | 语义 | 沿用字段 | 说明 |
> |---|---|---|
> | 启用 / 停用 | `is_active`（`:26`） | 管理端停用 → APP 下一次请求即 401，**本来就是现成逻辑** |
> | 未配置景区 | `scenic_id is NULL`（`:22`） | 现有模型本就允许为空 |
> | 角色 | `role`（`:23`） | 取值不变，Casbin 策略原样生效 |
>
> `password_hash:21` / `must_change_password:27` / `credentials_changed_at:29` **保留不动**：管理端还在用。

> **不再设计 `idp_provider` 列**：本次 IdP 就是票付通 3.0 一家，未来若接第二家，`tenantId` 本身就是天然区分维度，不必提前留一列用不上的第四范式。

### 2.3 IdP token 字段 → 我们怎么用（对照表）

| token 字段 | 落到哪 | 能否覆写本地字段 |
|---|---|---|
| `tenantId` | `idp_tenant_id` | — |
| `userId` | `idp_user_id` | — |
| `userName` | `idp_user_name`（镜像） | ❌ 不覆盖本地 `name`（管理 authoritative） |
| `phone` | `idp_phone`（镜像）+ **首次认人时用于匹配** | ❌ **不覆盖** `usr_users.phone`（唯一索引，且是管理端登录凭据） |
| `roles` | `idp_roles`（镜像） | ❌ **不参与鉴权**，见 §2.4 |
| `permissions` | `idp_permissions`（镜像） | ❌ **不参与鉴权**，见 §2.4 |

### 2.4 IdP 的 roles / permissions 怎么处理（**决策点，需你拍板**）

token 里带了 `roles` 和 `permissions`，但本次**建议一律不用**，理由：

1. 我们现有 APP 端权限是 `usr_users.role` → `governance_event_bus_service/policy.py` 的 `permissions_for(role, domain="app")`（`routes_app.py:184` /permissions 走的就是它）。**一旦两边都算权限，就得回答"谁说了算"，那是双权威，最难的 bug 都出在这里。**
2. 用户说"其他逻辑要保持不变"——权限判定保持不变，就是继续用我们的 `role`。
3. IdP 的角色编码跟我们的六值角色枚举（`super_admin/group_admin/group_developer/group_viewer/scenic_admin/scenic_operator`）大概率不是一套东西，映射关系还得另做。

**本次的用法分工**（二者不冲突）：

| 来自 IdP 的东西 | 怎么用 |
|---|---|
| `roles` | **落库不使用**——本地 `role` 继续管权限；IdP 侧改了角色不会让我们这边的权限跟着变 |
| `permissions` | **落库 + 用于过滤**：决定这个用户能看到哪些**分类的固定问题**（§11）。它不是"能不能进 APP"，而是"进来能问什么" |

一句话：**tab 能不能进归本地 `role`（Casbin），问题按分类过滤归 IdP `permissions`。** 想反过来（用 IdP 的权限替换我们整套 role 判定）是另一个独立改造，不在本次范围。

> 如果后续要用 IdP 的权限替换我们的 role 判定，那是**另一个独立改造**：要设计 IdP role→本地 role 的映射表、`/permissions` 改成读 IdP roles、缓存策略、映射缺失时的兜底。**不在本次范围。**

### 2.5 IdP 侧信息更新了，我们什么时候同步（**决策：运行时零滞后 + 镜像惰性刷新**）

先把"更新"这件事**按用途拆成两类**，答案完全不同：

| 用途 | 数据从哪来 | IdP 改完后多久生效 | 要不要同步 |
|---|---|---|---|
| **当次请求的判定**（身份、`permissions`/`roles` 若启用、`is_active`） | token claims + 本行现查 | **下一次 HTTP 请求即生效**（秒级） | ❌ 不需要——前提是**绝不读镜像列做判定** |
| **镜像列**（`idp_user_name` / `idp_phone` / `idp_roles` / `idp_permissions`） | 库 | 取决于刷新策略 | ✅ 唯一需要决策的部分 |

**按场景展开**：

| IdP 侧变更 | 落到我们这边 | 生效时刻 |
|---|---|---|
| 用户改名 / 改手机号 | 刷新 `idp_user_name` / `idp_phone` | **APP「我的」页看得到**（用户信息接口走我们这边），所以 `/api/app/me` 设为**即时刷新点** → 用户下一次点开个人资料就是新的；其余链路 ≤ 刷新窗口（谁为准见 §2.6） |
| 换手机号 | 同上 | **不影响登录**：认人按 `(tenantId, userId)`（§3），手机号只作镜像/首次匹配 |
| `roles` / `permissions` 变化 | **运行时从 token 取，不读列** | **用户下一次请求立即生效**，零滞后 |
| IdP 停用 / 删号 / 撤权 | 我们没有会话，靠 token 自然过期；IdP 有回调则置 `is_active=false` | TTL 到期，或回调后下一次请求立即 401（§8.2） |

> **最敏感的那类反而不存在滞后问题**：用户被 IdP 停用后能不能进来，取决于 token TTL（Q2）而不取决于我们有没有同步 —— 因为**不置换方案里我们压根没有会话状态**。这是这个方案相对"发自有 token"最大的安全优势。

**镜像列的刷新机制：惰性比对 + 时间窗口**（`idp_identity.py::maybe_refresh_mirror`）

```python
async def maybe_refresh_mirror(row, claims, window_seconds: int) -> bool:
    # 仅当值有差异 且 超过窗口才写；window_seconds 由调用方决定(分层见下表)
    ...
    update_idp_mirror(row, claims)   # 只写 idp_* 白名单列（§5 第 2 项）
```

**同一个函数、三档窗口**（调用频繁程度决定鲜度，而不是一刀切）：

| 调用点 | 窗口 | 理由 |
|---|---|---|
| 每请求鉴权链路（`deps.py`） | 默认 **24h**，走 `sys_settings`（`namespace="app"` / `key="idp.mirror_refresh_hours"`） | 高频且没人看这个值，几乎不写 |
| `POST /auth/sync`（登录） | 无条件刷新 | 登录是天然同步点，不用等窗口 |
| **`GET /api/app/me`（`routes_app.py:201`）** | **有差异即写**（`window=0`） | **用户信息展示接口，用户说得对——它就是镜像列的消费方**。调用频率极低（进个人页才调），多一次写毫无压力，换来"改完 IdP 资料，下次点开就是新的" |

> 上一版说"镜像滞后无人看得到"是**错的**：管理端列的是本地 `name` 没错，但 **APP 端用户信息接口返回的就是镜像**（§2.6），滞后用户直接看得见。这条按纠正后的结论处理。

**为什么不能"每请求都 UPDATE"**：`usr_users` 是被所有 join 依赖的核心表，每个 APP 请求都写一行会持续产生死元组（autovacuum 压力），且同一用户的并发请求会互相撞行锁。把高频链路的窗口放宽、把鲜度压力转移到低频的 `/me` 上，才是成本与体验都正确的分配。

### 2.6 APP「我的」页以 IdP 为准（**已定**）

**决策：APP 端展示的用户信息全部以 IdP 为准，改名字/手机号这类事我们这边不提供入口。**

分工就此明确：**用户的账号属性（姓名、手机号、密码）归 IdP，只有 `scenic_id` / `role` 归我们管理端**（§5.5 那套平行管理接口）。APP 前端要改用户资料，去找 IdP，不再经过我们。

落到代码：

| 位置 | 处理 |
|---|---|
| `routes_app.py:201 GET /me` | 保留并改造：姓名 / 手机号改取镜像列（向下兼容见下） |
| `routes_app.py:259 _app_profile()` | `"name"`: `idp_user_name or u.name`；`"phone"`: `_mask_phone(idp_phone or u.phone)`。**带 `or` 回落是因为存量管理端用户没有 `idp_*` 值**（多为NULL），不能让他们的 `/me` 变空 |
| `routes_app.py:217 POST /me` | **前端不再调用**，归入 §6 那批"本期不动、前端不用"的接口。改昵称的入口已迁到 IdP |
| `UpdateProfileRequest:212` | 不动（接口既然不调用，请求体也不用改） |

> **为什么不像上一版那样纠结 A/B**：因为改昵称本来就不该留两个入口。现在的判断很简单——既然 IdP 那边能改，我们这边的写入通道就是多余的，前端不用它就够了，不必在删除上花成本。

**顺带确定的两个展示口径**（不改也不影响鉴权，别挡主线）：`must_change_password` 对 IdP 用户恒 False；`last_login_at` 改由 `/auth/sync` 更新，否则 APP 端"最近登录"永远是空。

## 3. 认人：`(tenantId,userId)` 怎么落到 `usr_users` 那一行

**定好的规则**：以 `tenantId + userId` 为准——

- **查得到** → 只更新 `idp_*` 那一组信息（镜像 + `idp_synced_at`），**不动本地业务字段**
- **查不到** → **建号**（IdP 侧登录即可开户，不需要管理端先建）

> 注意：这改掉了 `routes_app.py:9-11` 里「APP 端仅登录、不可自注册」的老约定（该文件头注释要跟着改）。新语义是：**APP 不能在我们的注册页自己注册，但票付通那边的合法用户要能直接进来。**

### 3.1 建号时各列怎么填

`usr_users` 有几列是 `NOT NULL` 或有唯一索引，自动建号必须给确定值：

| 列 | 填什么 | 备注 |
|---|---|---|
| `id` | `uuid4()` | 与现有 `User` 一致（`models.py:17`） |
| `name` | IdP `userName` | 与本地 `name` 同源，**后续以 IdP 每次同步更新为准** |
| `phone` | IdP `phone` | ⚠️ **唯一索引**（`models.py:20`） |
| `account` | `f"idp_{tenantId}_{userId}"` | ⚠️ **唯一索引**（`:19`）。用 IdP 标识拼，保证不会撞管理端账号 |
| `password_hash` | **随机口令的哈希** | 列 `NOT NULL`（`:21`）。给随机串 → 密码登录必然失败：**这类账号只能从 IdP 进** |
| `role` | **`scenic_admin`（景区管理员）** | 默认走我们现有权限系统，见 §3.2 |
| `scenic_id` | 见 §3.3 ——**建号时为空** | 🔴 空值必须拦截，否则是集团级越权 |
| `is_active` | `true` | 现有默认（`models.py:26`） |
| `must_change_password` | `false` | 改密入口在 IdP，本地没有首登改密这回事 |
| `idp_roles` / `idp_permissions` | IdP 原值 | 落库画像，**不参与鉴权**（§2.4） |

**并发与唯一冲突（必须实现）**：同一个新用户并发两个请求时，两个事务都查不到 → 都 INSERT → 撞 `account` / `phone` 唯一索引报 `IntegrityError`。
处理：捕获 → 回滚 → **重新按 `(tenantId,userId)` 查一次**再放行（标准 upsert 语义），不能把这个异常透成 500。
另外 IdP 手机号若已存在于某个管理端账号上，也会撞 `phone` 唯一索引——这种情况按"已知账号"处理，把 `idp_*` 回填到那一行（等于路径 B），不要新建第二行。

### 3.3 🔴 未配景区 → **403「景区未配置」**，绝不能放行（集团级越权）

**这是自动建号必须先堵的洞。**

`deps.py:25` 的注释写得很清楚：`CurrentUser.scenic_id` 为 **None 表示「集团级」，数据归属集团而非某个具体景区**。也就是说——**空 scenic_id 不是"没配好"，而是"能看全部"**。

而 IdP 自动建的号，天然没有 `scenic_id`（它的景区归属只能靠管理端配，或靠 Q4 的 tenant→景区映射）。若直接放行：

```
新用户 → scenic_id=None → CurrentUser.scenic_id=None → 业务层当集团级处理 → 跨景区数据可见
```

所以必须拦截。拦截时的**语义与状态码**定如下：

| 项 | 取值 | 依据 |
|---|---|---|
| HTTP 状态 | **403** | 用户已经在 IdP 注册且登录成功，**认证是通过的**；被挡的是"授权/数据边界没定"，不是"你是谁没搞清楚" |
| 业务错误码 `code` | **2012 `AUTH_SCENIC_NOT_CONFIGURED`**（新增） | 沿用 `common/schemas.py:59-65` 里 2006-2011 那段「用户登录认证细分」，取下一个序号 |
| `message` | 「**账号尚未配置所属景区，请联系管理员**」 | 明确告诉用户下一步做什么 |

> **为什么不是 401**（这条最容易被拍成 401，但它是错的）：
>
> 1. **语义不符**：401 = 未认证。这里 IdP token 有效、身份明确，认证是全过的。
> 2. **项目里已有同样的分界线**：`ApiKeyInvalid`（**401**：Key 无效/吊销/过期，凭证本身有问题）vs `AgentNotAllowed`（**403**：Key 有效，但无权调这个 Agent）。我们的场景正是后者——**凭证有效，只是没有被授权访问任何景区数据**。
> 3. **401 会诱导客户端做错事**：APP 端看到 401 的通常处理是"token 失效 → 清本地 token → 重新登录"。但这个用户重登一百次结果都一样（配置没改），就变成了登录循环 / 反复弹"登录已过期"。403 的常规处理是"停在原页提示"，正是我们要的。
>
> 一句话：**401 叫用户"去登录"，403 叫用户"别动，等管理员"。** 这里是后者。

**顺带统一「账号停用」的返回**（同一类情况，别再散着写）：

| 场景 | HTTP | 业务码 |
|---|---|---|
| IdP token 无效/过期 | 401 | 沿用现有 `unauthorized` / `AUTH_TOKEN_INVALID(2008)` |
| 本地账号被停用（`is_active=false`） | **403** | 复用**已存在但没人用**的 `AUTH_ACCOUNT_DISABLED(2010)`（`schemas.py:64`）——别再新建 |
| 未配景区（`scenic_id` 为空） | **403** | 新增 `AUTH_SCENIC_NOT_CONFIGURED(2012)` |

**APP 前端按 `code` 分支**（这才是分出 401/403 的用处）：

- `2012` → 展示"等待管理员配置景区"，支持重试，但**不要**触发登出/重登
- `2010` → 展示"账号已停用"，同样不触发重登
- `2007/2008` → 才算"登录态没了"，可以走重新登录

配好景区之前，APP 端对这个用户的表现是"等待配置"，这是**预期分支**，不是故障。

> 如果 Q4 确认了 `tenantId` 与景区的对应关系，建号时可以直接写入 `scenic_id`，用户首次登录即可用——那时这条拦截依然存在（作为兜底），只是不再被触发。

**`/api/app/auth/sync` 这一个是例外**：sync 的目的是建档/认人，此时景区没配属于**正常状态**，所以 sync **返回 200**，在响应体里给一个 `status: "pending_scenic"` 让前端据此展示引导页，而不是抛 403。

**必须写死的红线（更新过的用户场景）**：

> **已存在的用户**：每次只能更新 `idp_*` 那一组列 + `idp_synced_at`；
> `account` / `phone` / `password_hash` / `scenic_id` / `role` / `is_active` / `last_login_at` **一律不动**（这些是管理端的资产）。
> **`scenic_id` / `role` 的权威永远在管理后台**——被 IdP 覆盖就等于跨景区越权。
>
> **建号时**（不存在的新用户）：一次性写入 §3.1 那张表的值，`phone` / `account` 也在其中——
> 这是「初始化」，不是「覆盖」；此后同样只能改 `idp_*`。

```python

async def get_current_app_user(authorization: str = Header(default="")) -> CurrentUser:
    if not authorization.startswith("Bearer "):
        raise Unauthorized("missing bearer token")
    token = authorization.removeprefix("Bearer ")

    # 1 验票并取出身份 —— token 里带齐了 tenantId/userId/phone/userName/roles/permissions
    claim = await idp_client.verify(token)     # 超时/失败一律 fail-close
    if not claim.valid:
        raise Unauthorized("invalid idp token")

    # 2 认人：(tenantId, userId) 是唯一标识 —— 有则更新 idp 信息，无则建号
    async with get_sessionmaker()() as db:
        user = await idp_identity.resolve_or_create(db, claim)   # 见下方说明

        if not user.is_active:
            # 403 + AUTH_ACCOUNT_DISABLED(2010)：身份有效但不放行，别触发客户端重登
            raise AccountDisabled("账号已停用")        # 管理端停用 → 下一次请求即生效

            raise ScenicNotConfigured("账号尚未配置所属景区，请联系管理员")

        cur = CurrentUser(user_id=user.id, scenic_id=user.scenic_id, role=user.role)

    set_trace_context(get_trace_id(), cur.scenic_id)
    return cur

请求期：deps.py:36 get_current_user 解码 + deps.py:52 _reject_if_credentials_changed
```

两个**容易被顺手改坏**的细节：

1. **`/auth/sync` 不要去更新 `last_login_at`**。
   `auth.py:113` 用 `last_login_at is None` 判断「首次登录」，决定是否强制短信验证码、是否触发改密。IdP 侧登录若把这个字段刷掉，同一个人**第一次登管理端会被当成老用户**，跳过本该有的验证与强制改密。APP 侧活跃时间用 `idp_synced_at` 记即可。
2. **纯 IdP 用户开户时，`password_hash` 要给"真随机口令的哈希"，不能给空串**。
   该列 `NOT NULL`（`models.py:21`），空字符串会让 `verify_password`（`auth.py:33`）处理非法哈希时行为不可预期；给随机串则密码登录必然失败——这正是要的效果：**这类账号只能从 IdP 进，管理端密码登录进不来**。

**双轨并存是常态**：同一个 `usr_users` 行可以既从管理端密码登录、又从 APP 端 IdP 登录，两条链路互不干扰，产出同一个 `user_id`——这也是旧表兼容版的又一个好处，不存在"两个身份各自一套数据"。

## 8. 两个要拍板的点

### 8.1 每请求调用几次 IdP

因为 **token 自带全部用户信息**，答案是：**只验一次 token**。

- `verify_mode=jwt`（本地验签）：**零网络调用**，只取 JWKS 定期刷新公钥
- `verify_mode=introspect`：每请求 1 次跨服务调用

这也是选不置换 + token 信息完整之后的最优解——不需要为"省一次 user_info 调用"纠结，因为没有这一步。

### 8.2 失效窗口归谁

不置换 = 失效窗口归 IdP，我们改不了。能做的只有三件：与 IdP 约短 TTL、争取撤权回调、高敏操作走实时校验。
**本地兜底仍然存在**：管理端停用账号 → `is_active=false` → 下一次请求即 401，这条不依赖 IdP。

## 9. 失败与降级

| 场景 | 行为 |
|---|---|
| `idp_verify` 超时/失败 | **fail-close，401**（身份不在我们手里，没有"先放行"的余地） |
| token 缺少 `tenantId` / `userId` | 401（标识不完整，无法确定身份） |
| `(tenantId,userId)` 查不到、`phone` 也匹配不上 | **401「账号未开通」**，前端提示联系管理员（预期分支，不是报错） |
| `is_active=false` | 401「账号已停用」，下一次请求即生效 |
| IdP 整体不可用 | APP 端新请求全 401。这是不置换的固有代价，01/05 已论证过 |

### 11.3.1 映射为什么放数据库（而不是 config.yaml）

三条理由，都是照着项目现有规矩来的：

1. **它是业务对照关系，不是部署参数**。IdP 那边的权限编码会长、会改、会按租户不同——这类东西放在 yaml 里，改一次要重启进程。项目里同类东西全部入库：`LlmModelConfig` / `ModelPrice` / `BudgetThreshold` / `ScenicOrg`（`governance_event_bus_service/settings.py:35-105`）、`AppScenicConfig`（`gateway_service/models.py:51`）。
2. **管理端本来就有写这个的地方**。`routes_app_admin.py:1-12` 的注释写着"这类配置是**运营在管理后台维护、APP 端消费**"——映射正是这个形态，塞进这个文件的 `/api/admin/app/*` 顺理成章，不用新开模块的权限体系（`ADMIN_ROLES` 已有）。
3. **`config/config.yaml` 属于部署基线**，按三层覆盖的规矩（`common/settings_models.py:11-16`）它管"默认值"，不该承载逐条业务数据。

表结构（照 `AppScenicConfig` 的写法）：

```python
class AppThemePermission(Base):            # gateway_service/models.py
    __tablename__ = table_name("app_theme_permission")
    __table_args__ = (
        UniqueConstraint("permission_code", "theme_code", name="uq_app_theme_permission"),
    )
    id              = String(36) PK default uuid4
    permission_code = String(128) NOT NULL   # IdP 的 permissions 里的编码原文
    theme_code      = String(64)  NOT NULL   # APP 分类:overview/passenger_flow/ticket/...
    remark          = String(255) default "" # 给运营看的备注
    updated_by      = String(48)
    updated_at      = DateTime(tz)
```

**唯一约束用 `(permission_code, theme_code)` 复合，而不是单独约束 `permission_code`**——这样一个权限天然可以放开多个分类（比如"景区数据全权"同时映射客流+票务），运营加一行就行，不需要改代码也不需要先拆表。

迁移 `0094`（追加在 `0093` 之后）：

```python
CREATE TABLE IF NOT EXISTS {P}app_theme_permission (
    id              VARCHAR(36) NOT NULL PRIMARY KEY,
    permission_code VARCHAR(128) NOT NULL,
    theme_code      VARCHAR(64) NOT NULL,
    remark          VARCHAR(255) NOT NULL DEFAULT '',
    updated_by      VARCHAR(48),
    updated_at      TIMESTAMPTZ DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_{P}app_theme_permission
    ON {P}app_theme_permission (permission_code, theme_code);
CREATE INDEX IF NOT EXISTS ix_{P}app_theme_permission_code
    ON {P}app_theme_permission (permission_code);
```

**读取方式**：这张表量很小（几十行），`list_fixed_for_app` 里**一次 `select` 全表**做内存映射即可，别为它引入进程级缓存——`observability/settings.py:1-16` 记着当初进程级 TTL 缓存连踩三个坑的教训（跨 loop 空缓存、worker 读默认），重蹈覆辙不值当。

### 11.4 语义要定死（**决策点**）

过滤涉及"空值代表什么"，不定清楚最容易出岔子：

| 情况 | 行为 | 理由 |
|---|---|---|
| 非 APP 链路 / 管理端用户（`permissions` 为空） | **完全不过滤**，与今天一致 | 不能伤到现有管理端行为 |
| APP 用户，`sys_settings` 开关关 | 不过滤（灰度期用） | 上线先跑老逻辑，确认 IdP 数据对齐了再开 |
| APP 用户，开关开、`permissions` 非空 | 按映射表转换后的白名单返回 | 目标态 |
| `permissions` 非空但**映射表里一条都没配** | **返回空 + 告警**（fail-close） | 映射没配 ≠ 全放行，这条最容易变成"漏配 = 全量开放" |
| APP 用户，开关开、`permissions` **为空** | **建议 fail-close：返回空列表 + 告警** | §9 的口径一致：身份已知、权限不明 → 不给数据。否则"没配权限"会变成"看全部" |

> 最后一条要你说一句：也可以选"空权限 = 不限制"（对运营最省事，但漏配权限 = 全量放开）。**默认建议 fail-close。**

### 11.5 影响面与两个补漏

走 `list_fixed_for_app` 的入口会全部跟着生效（`/agent/home` 首页选择器与 GuideCard、`/guide-questions`、`/panel/{theme}/insight`）——这是好事，不用一处一处改。

但有两处**不走这条链路、需要单独确认**：

1. **`/api/app/chat` 的问题命中**（`question_bank.match_question`）。用户如果绕过列表直接把某个 `question_id` 传进来，列表过滤就形同虚设。**建议命中后补一道校验**：该行的 `theme_code` 是否在白名单里，不在 → 403。
2. **`/api/app/followed-questions`**（关注列表）。用户关注的也是固定问题，要不要同样按权限过滤？建议同口径（否则能看到但不能问，状态很怪）。

不受影响的部分：预热派单（`prewarm_v2.py` 按景区+固定问题配置跑，与查看者权限无关）、管理端的问题库页面。
